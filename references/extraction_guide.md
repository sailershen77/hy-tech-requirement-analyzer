# 技术需求提取指南

本参考文档定义从项目需求书 docx 中提取技术需求与评分表的识别规则、分类体系和 Markdown 输出规范。

## 1. 技术需求识别规则

### 1.1 章节定位模式

通过标题文本定位"技术需求"区域。命中以下任一模式即视为技术需求章节的起始：

**章节标题模式（常见命名）**
- 技术需求 / 技术要求 / 技术参数 / 技术规格
- 技术规格书 / 技术规范 / 技术标准
- 功能需求 / 功能要求 / 业务需求
- 性能需求 / 性能指标 / 非功能需求
- 系统架构 / 平台要求 / 建设内容
- 实施方案 / 项目内容 / 建设目标

**章节标题模式（采购/招标类）**
- 采购需求 / 货物需求 / 服务需求
- 需求一览表 / 技术需求表 / 参数要求
- ★ 标注段落 / ▲ 关键参数

### 1.2 排除规则

以下内容**不属于**技术需求，应排除：
- 商务条款（付款方式、合同价款、投标保证金）
- 资格要求（企业资质、财务要求、业绩要求——除非与产品技术指标直接相关）
- 评标办法说明（评分方法描述本身，但评分表单独处理）
- 常见废标条款、纪律声明、格式要求
- 招标公告、日程安排、联系方式

### 1.3 技术需求语句识别

从正文段落中识别技术需求语句，使用以下特征：

**强约束词**（必须/应/应当/shall/must/需要/要求/不得/禁止）
**建议性词**（宜/建议/尽量/优先）
**可选性词**（可/可以/允许）

**量化指标模式**
- 性能："响应时间不超过X秒"、"并发用户数≥X"、"吞吐量X TPS"、"可用性≥99.X%"
- 容量："存储容量X TB"、"支持X万用户"、"数据量X条/年"
- 时间："X个工作日内"、"X小时内响应"、"故障恢复≤X分钟"

**技术要求引用模式**
- "符合/满足 GB/T XXXXX-XXXX《xxx》标准"
- "通过XXX认证/测评"
- "支持X协议（HTTP/HTTPS/TCP/WebSocket...）"

## 2. 技术需求分类体系

提取到的技术需求按以下分类组织：

### 2.1 系统架构类（架构/技术栈/部署）
- 架构模式（B/S、C/S、微服务、中台）
- 技术栈（语言、框架、数据库、中间件）
- 部署要求（容器化、私有化、云端、信创环境）

### 2.2 功能需求类（业务流程/功能模块）
- 核心功能模块及子功能
- 用户角色与权限
- 业务流程与状态流转
- 数据管理（录入、校验、存储、导出）

### 2.3 性能需求类（量化指标）
- 响应时间 / 吞吐量 / 并发数
- 容量与扩展性
- 可用性与容灾（RTO/RPO）

### 2.4 安全需求类
- 认证与授权（SSO、MFA、角色权限）
- 数据安全（加密、脱敏、备份）
- 合规（等保、密评、行业标准）
- 审计与日志

### 2.5 接口与集成需求类
- 对外接口（API、协议、数据格式）
- 第三方系统对接
- 数据交换与共享

### 2.6 运维与部署需求类
- 监控告警 / 日志管理
- 升级与回滚
- 培训与文档交付

### 2.7 其他技术要求
- 兼容性（浏览器、操作系统、信创适配）
- 易用性与可访问性
- 其他未归类的技术指标

## 3. 评分表识别规则

### 3.1 章节定位

标题命中以下模式即进入评分表区域：
- 评分表 / 评分标准 / 评标办法 / 评标细则
- 技术评分 / 商务评分 / 综合评分
- 评审因素 / 评分细则 / 分值构成

### 3.2 表格内容判断

表格命中以下任一特征即视为评分表：

**表头特征**
- 包含"评分项/评审因素/评分内容"
- 包含"分值/分数/权重/得分"
- 包含"评分标准/评分细则/评分说明"
- 包含"技术/商务/价格"作为评分分类

**内容特征**
- 行内包含"得分"、"扣分"、"加分"、"满分"等词
- 数值单元格为分值（如 5、10、20、30 分）
- 评分标准列描述得分条件（如"满足要求得X分"）

### 3.3 评分表结构提取

提取评分表时保留：
- 完整表头行
- 每行：序号、评分项名称、分值、评分标准/细则
- 表格前后的说明性文字（如"总分100分，技术65分商务35分"）
- 表格标题（若有）

### 3.4 非评分表排除

以下表格**不输出**为评分表：
- 技术参数响应表（属于技术需求本身）
- 商务报价表、价格明细表
- 资格证明文件清单
- 需求一览表（如无评分列）

## 4. Markdown 输出规范

### 4.1 输出结构

```markdown
# {文档标题} - 技术需求分析

> 文档信息：{项目编号} | 分析日期：{YYYY-MM-DD}

## 一、技术需求

### 1. 系统架构类
<!-- 每类一个标题，未提取到内容的类别不输出 -->

| 序号 | 技术需求 | 分类 | 约束程度 | 备注 |
|:---:|:---|:---:|:---:|:---|
| 1 | 系统应采用B/S架构 | 架构类 | 必须 | 2.1节 |

### 2. 功能需求类
...

## 二、技术评分表

> {评分方法说明文字，若无则不输出}

| 序号 | 评分项 | 分值 | 评分标准 |
|:---:|:---|:---:|:---|
| 1 | 技术方案 | 20 | 方案完整、合理、可行... |

<!-- 表格若跨越多个表格，按文档顺序分别输出 -->
```

### 4.2 技术需求表字段

| 字段 | 说明 | 取值 |
|---|---|---|
| 序号 | 全局顺序编号 | 1, 2, 3... |
| 技术需求 | 需求原文（清洗后） | 保留完整语义 |
| 分类 | 按第2节分类体系 | 架构/功能/性能/安全/接口/运维/其他 |
| 约束程度 | 需求强制程度 | 必须 / 建议 / 可选 |
| 备注 | 来源章节/编号/量化指标 | 如 "2.3.1节" |

### 4.3 约束程度判定

- **必须**：含 必须/应/应当/shall/must/要求/不得/禁止，或为★/▲标注项
- **建议**：含 宜/建议/尽量/优先/should
- **可选**：含 可/可以/允许/may，或无明显约束词

### 4.4 评分表输出要求

- 保持原表行列结构，单元格内容原样保留（含换行用 `<br>` 或空格分隔）
- 分值列右对齐
- 若文档含多个评分表（如技术评分表、商务评分表），分别输出，加小标题区分
- 若表格前有说明文字（总分构成、评分方法），以引用块形式附在表格前
- **未发现评分表时，输出"未在需求书中发现评分表"并结束第二部分，不要虚构**

### 4.5 需求去重与合并

- 同一需求在不同位置重复出现时，保留首次出现，备注中标注"另见X节"
- 表格中表达的技术参数需求（如参数响应表）同样纳入技术需求清单
- 段落与表格重复的需求，以表格为准（表格通常更精确）

## 5. 技术部分目录结构生成规则

分析完技术需求与评分表后，生成投标书"技术部分"的目录结构，用于投标响应或标书编制：在 Markdown 分析文档中以层级列表呈现（本节规则），并转换为 docx 章节骨架文件（5.4.1 规则）。该目录以评分表的技术评分项为章节骨架，以提取的技术需求为内容要点，帮助投标人组织标书内容、评委对号入座打分。

### 5.1 章节骨架：技术评分项 → 章节（首选）

评分表中属于**技术部分**的评分项（总分构成中技术分值对应的评分项，或评分项名称含"技术/方案/实施/服务/验收/培训/售后"等词）逐一映射为章节：

| 技术评分项（常见） | 映射章节标题 | 章节内容来源 |
|---|---|---|
| 实施方案 / 技术方案 | 1. 实施方案 | 总体思路、进度计划、资源投入、风险保障 |
| 服务方案 / 质量保证 | 2. 服务方案 | 服务响应机制、技术支持、质量保证体系 |
| 评价及验收方案 | 3. 评价及验收方案 | 验收流程、通过条件、交付物清单及样例 |
| 人员配备 | 4. 项目组织与人员配备 | 团队结构、人员资质与证明材料 |
| 培训方案 | 5. 培训方案 | 培训计划、课程与教材交付 |
| 售后服务 | 6. 售后服务方案 | 服务承诺、响应时效、升级保障 |

**章节与评分项映射硬性规则**：

1. **一级标题优先对应评分大项**：评分表中的大项/分类行（如"技术方案""实施方案"）映射为一级章节；仅当评分表为单层结构（无大项小项之分）时，每个评分项直接作为一级章节
2. **二级标题优先对应评分小项**：评分大项下的细分项/子行（如评分细则中"进度计划""人员配备"等子项）映射为该章节下的二级标题，标题文字与评分小项逐字对应
3. **章节顺序尽量跟评分顺序一致**：章节编排顺序按评分表行序，不按需求书章节顺序或分类体系顺序重排，便于评委按评分表顺序对号入座
4. **每个评分点都要有可定位的章节**：生成目录后逐一核对评分表每一行，确保每个评分点（大项或小项）在目录中有明确对应的一级或二级章节；确实无法对应或归属不明的评分点，在"章节与评分项对照表"中显式列出并标注【建议人工确认】
5. **不确定是否需要单独成章的内容，标注【建议人工确认】**：如某项技术需求或评分细则要点难以判断是否应单独设章（可并入现有章节，也可独立成章），在该章节标题末尾追加【建议人工确认】，由标书编制人复核决定；该标注在 Markdown 目录与 docx 标题文本中均保留

规则：
- 章节顺序按评分表行序；每个一级章节标题后标注分值：`1. 实施方案　〔20 分〕`
- 一级章节用数字序列号：`1.`、`2.`、`3.`…（不用"一、二、三"中文序号）
- 评分项名称与章节标题尽量**逐字对应**（如评分项"实施方案"→章节"实施方案"），便于评委对应打分
- 同一评分项含多个要点时拆分为二级章节，二级用两级数字序号：`1.1 项目概述与理解`、`1.2 现状分析与差距预判`
- 非技术评分项（类似业绩、企业实力、报价等）不进入技术部分目录
- 【建议人工确认】标注不影响编号与分值标注，格式示例：`1.4 数据迁移方案【建议人工确认】`（docx 标题文本中序号剥离后为 `数据迁移方案【建议人工确认】`）

### 5.2 内容要点：技术需求 → 章节

将提取的技术需求按分类映射到章节，作为各章节的"内容要点"：

| 技术需求分类 | 默认归属章节 |
|---|---|
| 架构类 | 实施方案（总体架构与技术选型） |
| 功能类 | 实施方案（功能需求响应）或最贴近的业务章节 |
| 性能类 | 实施方案（性能指标响应）或服务方案（质量保证） |
| 安全类 | 实施方案（安全设计）或服务方案（合规保障） |
| 接口与集成类 | 实施方案（接口对接方案） |
| 运维与部署类 | 服务方案（部署运维保障）或实施方案 |
| 其他类 | 归入最贴近章节，不强行拆分 |

每个一级章节下的二级标题（如"1.3 总体实施思路""2.2 质量保证体系"）由该章节承接的需求内容归纳得出，命名尽量与评分标准关键词一致（可行性、完整性、时间计划、服务响应、质量保证、验收方案、材料齐全）。

### 5.3 无评分表时的通用骨架（兜底）

未发现评分表时，使用以下通用骨架组织技术部分目录，按 5.2 映射填充内容要点：

```
1. 项目理解与现状分析
2. 总体技术方案（架构类 + 功能类需求响应）
3. 非功能需求响应（性能类 + 安全类）
4. 实施方案与进度计划
5. 服务方案与质量保证
6. 验收方案
7. 项目组织与人员配备
8. 培训与售后服务
```

### 5.4 输出格式规范

目录结构作为分析文档的**第三部分**输出（紧跟在评分表之后），含三块内容：

```markdown
## 三、技术部分目录结构

> 依据评分表技术评分项与技术需求生成，章节与评分项对应、分值标注，便于投标响应与评委打分。

### 1. 目录结构

1. 实施方案　〔20 分〕
   1.1 项目概述与理解
       - 建设背景与评估目标
       - 标准依据（引用需求书中引用的标准名称）
   1.2 现状分析与差距预判
   1.3 总体实施思路（按需求书服务/建设模块展开）
   1.4 实施进度计划（甘特图 / WBS / 关键路径）
   1.5 风险与保障措施

2. 服务方案　〔10 分〕
   2.1 服务响应机制
   2.2 质量保证体系

3. 评价及验收方案　〔10 分〕
   3.1 验收方案（依据 / 流程 / 通过条件）
   3.2 交付物清单及参考样例

### 2. 章节与评分项对照表

| 章节 | 对应评分项 | 分值 | 编制要点 |
|:---|:---|:---:|:---|
| 1. 实施方案 | 实施方案 | 20 | 可行性 / 完整性 / 合理性 / 时间计划 |
| 2. 服务方案 | 服务方案 | 10 | 服务响应 / 质量保证 |
| 3. 评价及验收方案 | 评价及验收方案 | 10 | 验收方案 / 材料齐全度 |
```

要求：
- 目录结构使用**数字序列号**编号：一级用 `1.`、`2.`、`3.`…，二级用 `1.1`、`1.2`、`2.1`、`2.2`…，三级内容要点可用 `- ` 列表或括号说明
- **不使用** `├──` / `└──` / `│` 等树形符号，也不使用"一、二、三"中文序号
- 二级标题在缩进上比一级多两个空格，保持层级清晰
- 分值标注格式统一为 `〔N 分〕`
- 对照表"编制要点"取评分标准中的关键词，不自行发挥
- 无评分表时用 5.3 通用骨架，并在说明行注明"（无评分表，采用通用骨架）"

### 5.4.1 目录结构 docx 输出（必做）

除 Markdown 主文档外，"技术部分目录结构"**必须**同时输出 docx 章节骨架文件（用 `scripts/outline_to_docx.py` 转换）：

| 目录层级 | Markdown 形态 | docx 标题文本 | docx 样式（硬性要求） |
|---|---|---|---|
| 一级目录 | `1. 服务方案　〔20 分〕` | `服务方案　〔20 分〕` | **标题 1**（Heading 1） |
| 二级目录 | `   1.1 项目理解与重难点分析` | `项目理解与重难点分析` | **标题 2**（Heading 2） |
| 三级要点 | `       - 评估目标（...）` | `评估目标（...）` | **标题 3**（Heading 3） |

- docx 标题文本中**去掉数字序列号**（`1.` / `1.1` / `1.1.1`，脚本自动剥离），只保留标题文字、标题样式、分值标注 `〔N 分〕` 与【建议人工确认】标注
- **每个标题行（Title / 标题 1/2/3）下面追加一个空行**（Normal 样式空段落），便于在骨架中直接填写章节内容
- **删除未使用的多余样式**：文档只保留 Normal、Title、Heading 1/2/3 五个样式（脚本自动清理），样式面板干净不干扰后续排版
- 编号如需要，由 Word"多级列表/定义新的多级列表"关联标题样式后自动生成
- Markdown 主文档中的目录结构仍保留数字编号（数字编号规则见 5.4）
- 文档首行为 Title 样式的文档标题（"{项目名} 技术部分目录结构"）
- 文件命名：`technical-part-outline-{日期}.docx`
- 用途：直接作为投标书技术部分的章节骨架——在 Word 中可用导航窗格查看结构、引用→目录自动生成目录、逐章填写标书内容

### 5.5 编制要点

- 每个技术评分项都必须在目录中有对应章节，不得遗漏；生成目录后逐行核对评分表（5.1 硬性规则第 4 条）
- 章节标题优先与评分标准关键词逐字对应，便于评委对号入座
- 一级标题对应评分大项、二级标题对应评分小项、章节顺序跟评分顺序一致（5.1 硬性规则第 1-3 条）
- 技术需求中的量化指标与硬性要求体现在对应章节的"内容要点"中
- 需求书中的关键不确定点（如评估时间以外部窗口为准）应单独设"应对预案"类章节，体现方案合理性
- 拿不准是否单独成章的章节，标题末尾标注【建议人工确认】，不擅自取舍（5.1 硬性规则第 5 条）

## 6. 常见坑与处理

| 情况 | 处理 |
|---|---|
| 文档无技术需求章节 | 提取全文所有含强约束词/量化指标的句子，归入最接近分类 |
| 技术需求在表格中 | 表格每一行视为一条技术需求，按列提取 |
